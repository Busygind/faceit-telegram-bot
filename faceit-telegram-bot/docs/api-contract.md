# FACEIT API: контракт и границы реализации

Проверено по официальной документации 15 октября 2026 года. 16 октября 2026 года проверены живые ответы для `aghori-`: профиль, две страницы истории, details и stats последнего завершённого матча вернули HTTP 200. Это не заменяет проверку всех режимов и 30-матчевого отчёта. Локальные тесты используют синтетические HTTP-ответы; они проверяют код, но не подтверждают доступ конкретного приложения FACEIT.

## Официальные источники

- [FACEIT Data API](https://docs.faceit.com/docs/data-api/data/) — методы и схемы ответов.
- [OpenAPI JSON](https://open.faceit.com/data/v4/docs/swagger.json) — параметры и числовые ограничения пагинации.
- [API keys](https://docs.faceit.com/getting-started/authentication/api-keys/) — создание ключа приложения.

## Используемые методы

Фиксированный HTTPS origin: `https://open.faceit.com/data/v4`. Все запросы — GET с `Authorization: Bearer <server-side-key>`. Адреса сторонних API, пароли FACEIT/Steam, cookies и пользовательский OAuth не используются.

| Метод | Назначение |
|---|---|
| `/players?nickname=...` | Разрешение явно указанного ника, `player_id`, наличие `games.cs2`, текущие ELO и уровень |
| `/players/{player_id}` | Свежий профиль сохранённого личного FACEIT, включая актуальный ник/ELO; без поиска по старому нику |
| `/players/{player_id}/history?game=cs2&from=...&to=...&offset=...&limit=100` | История одного запрошенного игрока |
| `/matches/{match_id}` | Завершение, составы, результат и счёт матча/серии |
| `/matches/{match_id}/stats` | Массив карт `rounds` с динамическими словарями показателей |

Для `/setfaceit ник` используется только запрос профиля по нику — история и статистика не загружаются. Для личных `/last` и `/stats` без аргумента профиль читается по сохранённому `player_id`, поэтому смена ника на FACEIT не переключает пользователя на другой аккаунт. Явный ник по-прежнему разрешается независимо от привязки. Сохранение ника — самообъявленная настройка, не подтверждение владения FACEIT через OAuth.

`history.from` и `history.to` — Unix **секунды**, `offset` — 0–1000, `limit` — 1–100. Без `from` API по умолчанию ограничивает историю месяцем, поэтому обе границы передаются явно. У другого метода `/players/{player_id}/games/{game_id}/stats` даты задаются **миллисекундами**; он намеренно не используется.

## Как выбираются последние матчи

- В `start` фиксируется `to`; `/last` запрашивает один матч, `/stats` — до 30.
- Первое окно — 90 дней. Если матчей недостаточно, нижняя граница последовательно расширяется вплоть до Unix epoch. 90 дней не являются скрытым ограничением выборки.
- Контракт не обещает сортировку страниц. Сначала дочитываются все страницы окна, потом игры сортируются по `finished_at` и устойчивому второму ключу `match_id`.
- Насыщенное окно с полной страницей при offset 1000 делится по времени. На HTTP-проводе каждое окно расширяется на одну секунду с обеих сторон (нижняя граница не меньше нуля), чтобы целые временные метки на стыке не терялись при строгих границах API. Повторы дедуплицируются по `match_id`; offset больше 1000 не отправляется.
- В выборку проходят только CS2 записи со статусом `FINISHED` и положительным `finished_at`, не позднее зафиксированного среза. Незавершённый/отменённый статус в details также исключает запись.
- Отсутствующие подробности не заменяются старой игрой ради красивого покрытия. Даже при stats 404 `/last` остаётся обзором фактического выбранного последнего матча.

Описание API не уточняет включительность обеих временных границ и поле, по которому применяется временной фильтр. Проводной верхний timestamp может быть на секунду больше среза; фильтр `finished_at <= to` всё равно сохраняет исходный фиксированный snapshot. Тесты проверяют строгие границы на разделителе окна, на отметке 90 дней и на секунде среза. После выдачи ключа необходима живая контрактная проверка самого временного поля и сопоставление с FACEIT matchroom. Код не выдаёт порядок API за документированную гарантию.

Если более 1100 записей не удаётся разделить в минимальном временном интервале, core возвращает `HISTORY_DENSITY_UNRESOLVED`, `done:false` и не публикует незавершённую выборку как окончательные последние матчи.

## Статистика и нормализация

Схема API описывает `round_stats`, `team_stats` и `player_stats` как словари произвольных ключей. Названия конкретных CS2 полей и их фактическая доступность должны быть подтверждены живым ответом. Парсер поддерживает числовые строки и известные варианты `Kills`, `Deaths`, `Assists`, `Headshots`, `Rounds`, `Total Damage`/`Damage`, `ADR`; отсутствие, отрицательное или нечисловое значение остаётся `null`.

Матч определяется по `match_id`, а карты BO3/BO5 сводятся внутрь него. Отдельные карты, дубли и явно несыгранные записи не увеличивают число матчей. Разрез карт считает сыгранные карты, включая повтор одной карты в серии.

Формулы используют парные доступные исходные данные одной карты, а не среднее готовых отношений:

- K/D: сумма убийств / сумма смертей.
- K/R: сумма убийств / сумма раундов.
- HS: 100 × сумма убийств в голову / сумма убийств.
- ADR: сумма урона / сумма раундов. Если доступен только ADR карты, он взвешивается по раундам и помечается `approximate:true`.
- Средние убийства: сумма убийств только полностью покрытых матчей / число таких матчей.
- Win rate: победы / матчи с известным исходом. Неопределённый исход не превращается в поражение.

Деление на ноль возвращает `null`, а не ноль или бесконечность. Каждая метрика отдельно сообщает число покрытых матчей и карт. Текущие ELO/уровень не интерпретируются как изменение за матч. Rating, KAST, swing и историческая ELO-дельта не рассчитываются без подтверждённого источника.

## Внутренний интерфейс

```javascript
const faceit = createFaceitService({ fetch, key, now });
const checkpoint = await faceit.start(nickname, 'last'); // либо 'stats'
const result = await faceit.advance(checkpoint, { maxRequests: 8 });
// result: { done, state, report, progress }
```

`now()` возвращает Unix секунды. Внедряемый `fetch` имеет SDK Response-интерфейс: `status`, `headers.get()`, `json()`. Checkpoint сериализуется в JSON, содержит публичные игровые данные и фазу, но не API-ключ, HTTP-заголовки или Telegram-реквизиты.

Отчёт включает `kind`, `nickname`, `playerId`, текущие `elo/level`, `requested/count`, `wins/losses/unknownResults`, `winRate`, `recent`, `range`, `updatedAt`, `partial`, `metrics`, `maps`, `matches`. Для `/last` дополнительно присутствует `match`. Метрика имеет форму `{ value, matches, maps }`. Изображение и текст получают один и тот же отчёт.

`partial:true` означает отсутствующие details, карты или исходные показатели. Отдельные покрытия остаются достоверными и при неполном отчёте. Если выборка истории ещё не закончена, `report:null`, а не якобы готовая статистика. Повторная новая команда заново обращается к источнику; продолжение уже готового job повторно данные не обновляет. Его исходное `completedAt` сохраняется, а результат старше пяти минут дополнительно получает `stale:true` — новая попытка доставки не выдаётся за обновление источника.

## Порции работы и ошибки

Размер порции — лимит **приложения**, не заявленная квота FACEIT. После порции Telegram-бот сохраняет checkpoint и предлагает кнопку «Продолжить»; фоновых таймеров и обещаний неограниченного времени Serverless нет.

429, 5xx и транспортная ошибка возвращают безопасное состояние паузы. `Retry-After` учитывается как число секунд или HTTP-дата; иначе применяется ограниченная экспоненциальная задержка с jitter. До `retryAt` новые GET не отправляются. 401/403 сообщаются владельцу без бесконечных автоматических повторов. Тела ошибочных ответов, исходные сетевые исключения и ключ не публикуются и не включаются в checkpoint.

Отдельная ручная приёмка должна подтвердить ключ приложения, фактические поля CS2, последние 1/30 матчей на тестовом профиле, BO3 при наличии и отсутствующую/задержанную статистику. До этой проверки запуск в реальном Telegram/FACEIT не считается завершённым.

## Проверка живых CS2 полей 16 октября 2026 года

- У последнего проверенного матча доступны `Kills`, `Deaths`, `Assists`, `Headshots`, `Headshots %`, `Damage` и `ADR`; источником являются разные показатели.
- `Headshots` — количество убийств в голову, `Headshots %` — процент. Символ `%` семантически значим: порядок ключей JSON нельзя использовать для выбора между этими полями.
- Регрессия покрывает процент перед количеством, обратный порядок и отсутствие количества. Процент сам по себе не подставляется вместо отсутствующего headshot-count.
- Лимит запроса, правила временного фильтра и прочие режимы остаются предметом отдельной контрактной приёмки; проверка одного профиля/матча не доказывает их полностью.
