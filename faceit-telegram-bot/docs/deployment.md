# Развёртывание и эксплуатация

## Временное локальное тестирование

Пока Telegram Serverless в листе ожидания, доступен отдельный Node.js 24 long-polling runner: [полная инструкция](local-testing-ru.md). Команды `npm run local:check` и `npm run local` не требуют npm-зависимостей, VPS или домена. Обычный токен BotFather используется только локально. Runner не удаляет webhook и не публикует код.

Перед облачным `webhook sync` остановить локальный процесс через `Ctrl+C`. Локальная `.local-data/bot.sqlite` и её `.secrets/local-encryption.json` не мигрируют в Serverless автоматически. Для MVP после перехода заново задать TeamSpeak командой в нужной группе. Не удалять локальный ключ, пока нужны сохранённые локальные данные.


## Платформа

Выбран [Telegram Serverless](https://core.telegram.org/bots/serverless), документация проверена 15 октября 2026 года (CLI 0.2.0). Runtime — JS V8 с `sdk`/`sdk/db`, встроенными Bot API, SQLite и outbound HTTP. Собственный VPS, домен, TLS и polling daemon не используются.

Не документированы стоимость, квоты CPU/memory/time, секретное env-хранилище, scheduler, транзакционный batch и штатный backup/restore API. Не принимать их наличие или бесплатность за гарантированные. Доступность Serverless конкретному боту проверяет владелец в BotFather.

## Текущий статус

`@road_to_3_elo_bot` создан; доступ к Telegram Serverless запрошен, пока лист ожидания. До одобрения нельзя пройти Telegram Serverless CLI login и публикацию на этой платформе. Текущая облачная копия работает на Sites; локальный runner — резерв. Подготовить FACEIT key можно независимо от Telegram. Тестовый ник — `aghori-`, пример тестовой супергруппы — `chat_id -1004393474895`; этот ID не ограничивает доступ.

## Инсталляция после одобрения Serverless

См. [подробный пользовательский гайд](getting-started-ru.md) и README. Node 24 нужен локально, не в облаке. `npm ci` восстанавливает только lockfile; runtime библиотеки зависимостей не загружает.

```bash
npx tgcloud login
npm run configure -- --faceit-key-file /Users/busygind02/IdeaProject/faceit-telegram-bot/.secrets/faceit.key
npm run deploy -- --dry-run
npm run deploy
npx tgcloud migrate --dry-run
npx tgcloud migrate
npx tgcloud webhook sync
npx tgcloud webhook
```

Список разрешённых чатов отсутствует; `configure` не требует `--chat-id` или `--bootstrap`. Добавить бота и выдать права можно в любой группе/супергруппе без изменения конфигурации. TeamSpeak и личные FACEIT-привязки остаются раздельными по чатам, `/setts` — только для администратора текущей группы. Рабочие команды в личке и каналах не поддерживаются. Открытое подключение групп увеличивает общий расход FACEIT API и хостинга; ограниченные задания и rate limit не гарантируют квоты на каждую группу.

CLI token вводится интерактивно, сохраняется в управляемой CLI папке `.tgcloud/`. Не читать и не редактировать её вручную. Для собственного CI CLI поддерживает `TGCLOUD_TOKEN`; значение выдаётся менеджером секретов без echo. FACEIT key можно передать через уже приватно настроенную `FACEIT_API_KEY`, не через аргумент команды. Предпочтителен mode-0600 файл.

Запускайте cloud `run` только в тестовой группе: он действительно выполняет сетевые отправки и пишет в облачную базу, хотя не публикует код. Никогда не помещайте реальные TeamSpeak реквизиты в аргумент `tgcloud run`, shell history, тесты или логи.

## Что загружается

- `tgcloud/schema.js`, `tgcloud/lib/**/*.js`, `tgcloud/handlers/*.js`.
- Private settings тоже загружается: `.gitignore` не является фильтром Telegram deployment.
- Документация, тесты, локальные `.secrets`, исходный шрифт и генераторы остаются локально.
- Нет Mini App `static`, публичного сайта, пользовательских endpoints или обработчика `poll_answer`.

При обновлении кода `deploy` делает preflight и `push`, но не меняет схему. `migrate` — отдельная reviewed операция. После изменения набора handlers нужен `webhook sync`; не удаляйте pending updates через `--drop-pending` без необходимости.

## Обновление и откат

Перед обновлением: тесты → проверка импорта/синтаксиса → защищённая копия конфигурации → deploy. Не используйте общий `tgcloud diff` для вывода секретного generated module. Сравнивайте открытые исходники обычным редактором/VCS, private config — только внутренней проверкой `deploy --dry-run` без вывода значений.

Откат кода: восстановите предыдущие проверенные открытые модули из своего VCS/архива, оставляя актуальный private module и ключ, затем выполните обычный deploy. Не делайте `push --force`, если CLI сообщает чужую ревизию. Не откатывайте схему деструктивно ради отката JS; сначала проверьте совместимость.

## Резервирование и ключи

- SQLite принадлежит платформе и сохраняется между вызовами. Это не равно гарантированному backup. В изученной справке нет проверенного bulk backup/restore механизма: выясните доступные средства BotFather/поддержки до эксплуатации важных данных.
- Сделайте зашифрованную отдельную копию `.secrets/runtime.json`. Потеря этой копии при сохранной облачной базе лишает доступа к TS ciphertext. Генератор откажется молча заменить существующий private module при утрате исходного key file.
- FACEIT key можно заменить повторным `configure` с тем же `.secrets/runtime.json`, затем deploy: TS ключ не меняется.
- Ротация TS encryption key требует офлайн расшифровки всех записей старым ключом и повторного шифрования новым либо явного повторного `/setts` в каждой группе. Автоматическая бесшовная ротация в MVP не реализована; не меняйте ключ вручную.
- После восстановления старой базы сохраняйте исходный ключ и проверьте версии TS. GCM-SIV выбран как защита от катастрофического nonce-reuse обычного GCM при rollback, но сам rollback всё равно требует проверки. Ключи разных независимых установок не копировать.

## Диагностика

1. `tgcloud webhook`: платформа получает нужные update types; в облаке должны быть только message и callback_query handlers.
2. `/setup`: правильный ли это групповой чат, какой у него ID, есть ли у бота права администратора и отправки. Telegram гарантирует проверку чужого membership через getChatMember только для бота-администратора.
3. Плохой FACEIT key/401/403: не повторять бесконечно; перевыпустить Server side key и обновить private config.
4. 429/5xx: дождаться retryAt и нажать «Продолжить». Invocation не живёт в фоне. Можно уменьшить maxRequests в защищённом конфиге с повторным configure/deploy после оценки лимита среды.
5. Кнопка устарела/другой чат/тема: новый запрос с ником в нужной теме; не менять чужой job адрес доставки.
6. После outcome_unknown опроса/фото сначала посмотреть чат. Автоматический POST retry запрещён. Новый явный запрос может дублировать уже доставленный результат — это осознанное действие человека.

Не включать логирование HTTP headers, текста команд, callback с секретами, сырых updates и JSON errors. В коде runtime нет console-логов. Локальный CLI/admin видит серверные модули — защищать его как production доступ.
